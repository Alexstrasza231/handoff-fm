# 刷新一下，正在干活的 AI 怎么没了？

[English](./refresh-selection.md) · [后台回归测试](../../tests/run-order.test.ts) · [浏览器回归测试](../../tests/browser/run-selection.spec.ts)

[经检查的真实事件顺序](./refresh-events.json)包含派活到交稿的 99 条记录：内容字段全部排除，实例使用别名，时间改为相对时间，证据等级原样保留。[截图](../media/refresh-case.png)展示的就是这份离线投影。

这是开发 HandoffFM 时在 Windows 上遇到的真实问题：一条较早创建的协作明明还在产生新记录，页面刷新却选中了另一条不活跃的任务。手动选回去，再刷新，选择又丢了。

**蓝鲸交了稿，白龙还得确认：现在看的到底是哪一桌？**

多条 AI 任务交错时，HandoffFM 的用途是找回正在看的协作，打开交接证据，再分别核对修改和验证。角色负责让过程好看，记录负责回答“谁做了什么”。

| 环节 | 这次真正做了什么 | 对照证据 |
| --- | --- | --- |
| Codex 复现 | 先写后台和浏览器回归测试，确认旧代码确实失败。 | 上方测试文件。 |
| 派给 DeepSeek | 通过 HandoffFM 包装器，只委派后台任务排序修复。 | 本地实际委派与工具记录。 |
| DeepSeek 修后台 | 收到新活动时，将对应任务重新插到 Map 末尾，再反向返回；保留标题、计数、原始时间。 | [后台源码](../../src/server.ts)，鉴权逻辑没有改动。 |
| Codex 修页面 | 在当前标签页内记住用户手选的实时任务；记录已不存在时回到最新任务。示例与离线回放不覆盖实时选择。 | [选择逻辑](../../web/data.ts)、[页面](../../web/App.tsx)。 |
| Codex 验证 | 检查补丁，运行核心测试、浏览器测试、类型检查与构建。 | 可按下方命令复跑，并查看 GitHub CI。 |

原因很小，但很容易漏：`Map.set` 更新已有键时不会改变顺序。原来返回的是“最后创建的任务”，不是“最近收到活动的任务”。直接按代理时钟排序也不可靠，因此改成按本地日志接收顺序。

下面是**回归测试用的复现数据，不是虚构的代理协作**：

```text
接收顺序：A 开始 → B 开始 → A 又有了新活动
修复之前：B、A
修复之后：A、B
```

A 的最后一条事件故意带着更早的代理时间，结果仍应排在最前面。同时，用户如果主动选择 B，刷新就继续看 B。系统默认选最新，与尊重用户手选，两者都要成立。

在源码目录复跑，需要 Node.js 22.12+：

```sh
npm ci
npm run check
npx playwright install chromium
npm run test:browser
```

后台测试走真实收集器和带令牌的本机接口。浏览器测试实际选择任务、刷新、进入示例再刷新，并验证已删除的选择会安全回退。

这次 DeepSeek 的沙箱运行常规 `tsx` 测试遇到了 `spawn EPERM`。它交稿时报告了 Node 原生方式的替代验证；Codex 在本机独立运行了标准 `npm run check` 和浏览器测试。因此，交稿与验收要分别核对。

实际使用时，启动 `handoff-fm watch`，让 Codex 通过包装器派一个范围明确的修复任务；点击**重播最近交接**看派活和交稿，点文件包看具体任务与结果，再点**查看最近修改**检查记录到的差异。交稿只是待检查，绿色命令只代表该命令通过。

本例不声称省了多少时间或 Token，也不保证覆盖所有桌面操作。并发修改和外部工具流不能确定精确写入者，文件变化仍保留 `unknown`。DeepSeek 与 Codex 的运行环境可能不同，最终验收需要实跑。本页不公开私有提示词、绝对路径或原始输出。
